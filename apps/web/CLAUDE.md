## Web app structure (the important split)

All builder/tracker **logic is pure and in `apps/web/src/model/`** (`doc.ts` doc transitions, `prereqs.ts`, `skills.ts`, `hp.ts`, `buffs.ts`, etc.) — tested directly with no DOM. React components in `components/` are thin views. `state/useCharacter.ts` is the **only** binding layer: model transition → `compute()` → Dexie. When adding a feature, put the logic in a `model/` module with tests, then wire a thin component.

- **RefData in the browser**: `data-pipeline`'s `loadRefData()` is Node-fs based; the app instead uses `src/refdata/loader.ts` (fetch). `scripts/copy-refdata.ts` copies vendored JSON into `public/data/` at predev/prebuild (gitignored — source of truth stays in the package), minus `monsters.json`/`monster-templates.json`, which only the reference site reads. `refdata/loader.ts` is the _only_ place that knows where data lives, so Stage 5 can swap in lazy R2 loading there. It reads through `src/refdata/cache.ts`, an IndexedDB store (`pf1-refdata`) keyed per file by its sha256 from `meta.json`'s `hashes`: `meta.json` is fetched first and always revalidated, and a bump refetches only the collections whose hash moved. Every cache operation degrades to a miss, so nothing there can break a load.
- **Persistence**: IndexedDB via Dexie (`src/db/characters.ts`, database `pf1-tracker`) is the source of truth; one active character; autosaves and restores most-recently-edited on load. `src/sync/` (Stage 5) layers optional background push/pull to `apps/api` on top — pure decision logic in `sync/planSync.ts`, a thin `fetch` wrapper in `sync/client.ts`, orchestration in `sync/backgroundSync.ts`, all wired into `state/useCharacter.ts`. Degrades to a complete no-op when `VITE_API_URL` is unset.
- **Schema migrations**: `model/migrations.ts` is an ordered chain of small idempotent steps, each declaring the `schemaVersion` a doc carries once it has run. `migrateDoc()` (Dexie reads, sync pulls) applies only the steps above the doc's own version and never downgrades a doc from a newer build; `migrateImportedDoc()` (file import) runs every step regardless, because a `schemaVersion` we didn't write is not evidence the steps ran. Adding a backfill means appending a step and bumping `CURRENT_SCHEMA_VERSION`, never editing a shipped one. **Dexie's own `version()` stays at 1 permanently** unless the object stores or indexes change: it governs the store/index layout, not the value shape, and `characters: "id, updatedAt"` is one blob keyed by id. Doc shape changes belong to the chain above, so a Dexie bump is only ever needed for a new index, a new store, or a key change.
- **Where you are is a URL fragment**: `model/appLocation.ts` (pure parse/format) + `state/useAppLocation.ts` (the browser binding) own `#/<mode>[/<section-id>]`, mirrored into localStorage so a reload with no fragment still restores. Nav rails report their scroll-spy section up via `onActiveChange`; `App.tsx`'s `useRestoreSection` scrolls back once on load. The binding must never overwrite a fragment it can't parse — `sync/session.ts` consumes `#session=<token>` late in the load, and stomping it breaks sign-in. `components/ReferenceLink.tsx` is the only place that knows the companion reference site's URL.
- **Vite/workspace-TS gotcha**: `@pf1/engine` and `@pf1/schema` publish raw `.ts` (no build step). `apps/web/vite.config.ts` aliases the bare specifiers to their `src/index.ts`; Vite's resolver handles their internal `./foo.js` → `./foo.ts` fallback. Keep these aliases in sync if package entry points move.
