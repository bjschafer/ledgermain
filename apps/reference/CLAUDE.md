## Reference site structure

`@pf1/reference` (port 5174, root script `dev:ref`) is a standalone read-only lookup site for the same vendored data the sheet uses, deployed on its own Worker at **`ref.ledgermain.app`**. It shares `packages/engine` and `packages/schema`; it shares **no code** with `apps/web`. The sheet reaches it only through `apps/web/src/components/ReferenceLink.tsx`, the one module that knows this site's URL.

Same split as the web app: **pure logic in `src/model/` and `src/shared/`**, tested directly; components in `src/components/` are thin views. `src/shared/` is the subset both the browser and the build-time generator import, so a change there has two callers.

- **Static payload, not a bundle**: `scripts/build-ref-index.ts` (predev/prebuild) reads `packages/data-pipeline/data/` and emits a columnar search index plus fnv1a-hash-bucketed ~32-entry shards into gitignored `public/ref/`. A page load fetches exactly two things: the index once, and the one shard holding whatever was clicked. Nothing records which shard an entry lives in; the client recomputes `bucketForId` from the id in the URL, which is why `src/shared/bucketing.ts` is imported by the generator rather than reimplemented. `src/data/loader.ts` is the only module that fetches reference data. The generator also copies the repo-root `OGL.txt` and `NOTICE.md` into `public/` — the OGL requires the license travel with the content.
- **Routing is a hash, hand-rolled** (`src/hooks/useHashRoute.ts`): four routes, no history state, so a router would cost more than the feature. `#/summon/...` is a **deep-link contract** the sheet calls into: unknown params and slugs are ignored, existing param names never change meaning, additions only. A detail URL's `?s=<id>` scrolls a rules page to the element stamped `data-section="<id>"`; query-only hash changes keep the scroll position, which is what makes the in-page jump list work.
- **Rules are pages plus sections.** `rules.json` (data-pipeline `transform/rules.ts`) is a tree: each entry carries its `path`, two levels of `children`, and its headings/run-in heads as `sections`. The generator indexes every page, plus each section whose title isn't generic (appears on more than `GENERIC_SECTION_PAGES` pages) as an extra row sharing its page's id with an `anchor` — so "use a scroll" lands on the paragraph inside Use Magic Device. Section rows are not entries: `countByCollection` and the generated-index counts skip them.
- **Engine imports go through the subpath alias.** `vite.config.ts` aliases `@pf1/engine/formula` ahead of the bare `@pf1/engine`, because the engine declares no `sideEffects: false` and pulling its barrel in for two formatters puts the whole rules engine in the bundle (166 KB → 484 KB). Mirror any alias change in `tsconfig.json`'s `paths`. `@pf1/data-pipeline` is deliberately not aliased: it is Node-fs based and must never reach the browser.
- **Cross-references don't resolve, except between rules pages.** `@UUID[...]` links are destroyed at data-build time (`resolveFoundryMarkup` in `packages/data-pipeline/src/util/html.ts`). The rules transform is the exception: a link to another rules page survives as `<a data-rule="<id>">`, which `RuleView` turns into this site's href. Links into other collections would need the same marker treatment in their transforms, not a client-side resolver.
- **Design tokens come from `@pf1/tokens`**, shared with the sheet. Don't copy palette or type values in; add app-specific ones to `src/styles.css`.
- **Feedback is the one request off this origin.** The footer's "Send feedback" (`src/data/feedback.ts`) posts to the API Worker's `/api/feedback`, the same endpoint the sheet uses, with its own copy of the form rather than shared code. It renders only when the `VITE_API_URL` and `VITE_TURNSTILE_SITEKEY` build variables are set (`.env.example`); the API admits this origin through `FEEDBACK_ONLY_ORIGINS`, and the Turnstile widget must list this hostname. A category id must stay in the Worker's allow-list.
- **Deploys itself.** Workers Builds is wired to this app the same way it is for `web` and `api` (see `CONTRIBUTING.md`): a push to `main` touching `apps/reference/**` or `packages/**` deploys it. Never run `wrangler deploy`.
